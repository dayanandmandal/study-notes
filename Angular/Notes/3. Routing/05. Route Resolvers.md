# Route Resolvers

## What Is a Resolver

A resolver fetches data before route activation.

It ensures component gets required data at start.

---

## Basic Resolver Example

```ts
import { ResolveFn } from '@angular/router';
import { inject } from '@angular/core';
import { UsersService } from './users.service';

export const userResolver: ResolveFn<User> = (route) => {
  const users = inject(UsersService);
  const id = route.paramMap.get('id')!;
  return users.getUserById(id);
};
```

Route config:

```ts
{ path: 'users/:id', component: UserDetailsComponent, resolve: { user: userResolver } }
```

Access in component:

```ts
const user = this.route.snapshot.data['user'];
```

---

## When to Use Resolvers

Good fit:

- detail page needs critical data before render
- page should not flash empty placeholders first
- SEO/server rendering flow benefits from data-ready navigation

Not ideal:

- non-critical widgets
- data that can load progressively after initial paint

---

## Error Handling Strategy

If resolver fails, decide navigation policy:

- redirect to fallback route
- return default-safe data
- fail navigation and show dedicated error route

Interview expectation: show that you plan explicit failure behavior, not silent errors.

---

## Resolver vs Component Fetching

Resolver:

- pros: component starts data-ready
- cons: navigation waits for data

Component fetching:

- pros: route activates quickly
- cons: loading state handling needed inside component

Senior answer: choose based on UX criticality and time-to-interactive goals.

---

## Common Mistakes

- using resolvers for every route and slowing navigation globally
- not handling resolver errors
- tightly coupling resolver to component-specific formatting logic

---

## 5 Years Interview Quick Lines

- Resolver is for critical pre-activation data.
- Keep resolver focused on retrieval, not UI transformation.
- Balance data-readiness vs navigation speed.
