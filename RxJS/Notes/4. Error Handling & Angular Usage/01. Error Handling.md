# RxJS Error Handling

---

# Observable Error Contract

An Observable can only do one of three things:

```text
1. emit values
2. complete
3. error
```

Once an Observable errors:

```text
It terminates permanently.
```

Example:

```text
1
2
3
ERROR
```

After error:

```text
No more values
No complete
```

This is the reason error handling operators exist.

---

# catchError()

```ts
function catchError(fn) {
  return function (source$) {
    return new Observable((subscriber) => {
      const sourceSubscription = source$.subscribe({
        next(value) {
          subscriber.next(value);
        },

        error(err) {
          // 1. error happens → run handler
          let fallback$;

          // if there is any issue with fallback, it directly throws the error as fallback is not correct
          try {
            fallback$ = fn(err);
          } catch (e) {
            subscriber.error(e);
            return;
          }

          // 2. unsubscribe from source (it's dead anyway)
          sourceSubscription.unsubscribe();

          // 3. subscribe to fallback Observable
          fallback$.subscribe({
            next(value) {
              subscriber.next(value);
            },
            error(e) {
              subscriber.error(e);
            },
            complete() {
              subscriber.complete();
            },
          });
        },

        complete() {
          subscriber.complete();
        },
      });

      // teardown logic
      return () => {
        sourceSubscription.unsubscribe();
      };
    });
  };
}
```

Purpose:

```text
Catch an error and return a new Observable.
```

Signature:

```ts
catchError((error) => ObservableInput);
```

Example:

```ts
http.get("/users").pipe(
  catchError((error) => {
    return of([]);
  }),
);
```

Result:

```text
Error occurs
↓
catchError executes
↓
Fallback Observable returned
↓
Stream continues
```

### Important analogy

```text
Think of catchError like:

If train crashes → you switch to a bus
You are NOT restarting the same train
```

```text
catchError replaces the error stream only within the current subscription pipeline; it does not propagate or cache fallback values for future subscribers.
```

---

# Why Return an Observable?

Wrong:

```ts
catchError((error) => {
  return [];
});
```

Correct:

```ts
catchError((error) => {
  return of([]);
});
```

Because:

```text
catchError must return an Observable.
```

# Common catchError Patterns

## Return Fallback Data

```ts
catchError(() => of([]));
```

Example:

```text
User list API fails
Show empty list
```

---

## Return Default Object

```ts
catchError(() =>
  of({
    id: 0,
    name: "Unknown",
  }),
);
```

---

## Rethrow Error

```ts
catchError((error) => {
  return throwError(() => error);
});
```

Use when:

```text
You want to log error
But still allow caller to handle it
```

Example:

```ts
catchError((error) => {
  console.error(error);

  return throwError(() => error);
});
```

# Where Should catchError Be Placed?

Example:

```ts
source$.pipe(
  switchMap(() =>
    http.get(...)
  ),
  catchError(...)
);
```

Step-by-step:

```
source$ emits
↓
switchMap runs
↓
HTTP request starts
↓
HTTP errors ❌
↓
catchError INSIDE HTTP handles it
↓
returns of([])
↓
switchMap receives [] as normal value
↓
NO ERROR propagates outward
```

This catches:

```text
Source errors
SwitchMap errors
HTTP errors
```

# RxJS Flow: switchMap + HTTP Error + catchError (Outer Level)

---

## Flow

source emits A  
→ switchMap → HTTP(A) ❌ error  
→ error bubbles out of switchMap  
→ catchError runs  
→ stream is replaced

---

## Important Result

The whole pipe is replaced → original source pipeline is DEAD

---

## What this means

- ❌ source$ will NOT continue inside this same stream
- ❌ no more switchMap triggers from this chain
- ✔ only fallback stream continues

---

## Key Insight

catchError at outer level does NOT recover the same stream  
It replaces the entire Observable chain with a new one

---

## Final Mental Model

Error inside switchMap → bubbles out → catchError replaces entire pipeline

---

Inside switchMap:

```ts
source$.pipe(
  switchMap(() =>
    http.get(...).pipe(
      catchError(() => of([]))
    )
  )
);
```

This catches:

```text
Only HTTP errors
```

Source stream continues.

Interviewers often ask this.

# retry()

Purpose:

```text
Automatically resubscribe after error.
```

Example:

```ts
http.get("/users").pipe(retry(3));
```

Meaning:

```text
Try 1
Fail

Try 2
Fail

Try 3
Fail

Try 4
Fail

Error emitted
```

Total attempts:

```text
Original + retry count
```

So:

```ts
retry(3);
```

means:

```text
4 attempts total
```

---

# When To Use retry()

Good candidates:

```text
Network timeout
Temporary server issue
Connection reset
```

Bad candidates:

```text
401 Unauthorized
403 Forbidden
404 Not Found
Validation errors
```

Retrying these usually makes no sense.

Example:

```ts
http.get('/users').pipe(
  retry(2),

```

Flow:

```text
Request
↓
Fail
↓
Retry
↓
Retry
↓
Fail
↓
catchError
```

Important:

```text
catchError executes only after all retries fail.
```

# retryWhen() (Advanced)

Purpose:

```text
Retry using custom logic.
```

Instead of:

```ts
retry(3);
```

You decide:

```text
When to retry
How many times
How long to wait
```

---

# Example Retry With Delay

```ts
http.get("/users").pipe(retryWhen((errors) => errors.pipe(delay(2000))));
```

Flow:

```text
Fail
Wait 2 seconds
Retry
```

---

# Example Limited Retries

```ts
retryWhen((errors) =>
  errors.pipe(
    scan((count, error) => {
      if (count >= 3) {
        throw error;
      }

      return count + 1;
    }, 0),

    delay(1000),
  ),
);
```

Meaning:

```text
Retry max 3 times
Wait 1 second between retries
```

---

# Exponential Backoff

Senior-level topic.

Instead of:

```text
1 sec
1 sec
1 sec
```

Use:

```text
1 sec
2 sec
4 sec
8 sec
```

This reduces server pressure.

Typical production systems use exponential backoff.

# Error Handling With switchMap

Interview question:

```text
Search API fails.
Should entire search stream die?
```

Bad:

```ts
search$.pipe(
  switchMap(term =>
    http.get(...)
  ),
  catchError(...)
)
```

After error:

```text
Entire stream dies.
```

User cannot search again.

---

Better:

```ts
search$.pipe(
  switchMap(term =>
    http.get(...).pipe(
      catchError(() => of([]))
    )
  )
)
```

Result:

```text
One request fails
Search stream survives
Next search still works
```

Very common Angular interview question.

# Angular HttpInterceptor vs catchError

Question:

```text
Where should global error handling go?
```

Answer:

```text
HttpInterceptor
```

Examples:

```text
401 handling
Token expiration
Logging
Global notifications
```

Use catchError for:

```text
Feature-specific fallback logic
```

Examples:

```text
Empty table
Default value
Custom UI handling
```

# throwError()

Purpose:

```text
Create an Observable that immediately errors.
```

Example:

```ts
return throwError(() => new Error("Something failed"));
```

Commonly used inside:

```ts
catchError();
```

# Interview Questions

## What happens after an Observable errors?

```text
Observable terminates.
No more values are emitted.
```

---

## Why use catchError?

```text
To recover from an error by returning another Observable.
```

---

## Difference between catchError and retry?

```text
retry:
Attempts operation again.

catchError:
Handles final failure.
```

---

## When should retry not be used?

```text
401
403
404
Validation failures
Business rule failures
```

---

## Difference between retry and retryWhen?

```text
retry:
Fixed retry count.

retryWhen:
Custom retry strategy.
```

---

```text
Increasing delay between retries.

1s
2s
4s
8s
...
```

## Where should global API error handling live?

```text
HttpInterceptor
```

```text
To prevent the outer stream from terminating.
```
