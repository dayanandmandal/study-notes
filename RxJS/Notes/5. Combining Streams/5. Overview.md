# RxJS Join Operators: Behavioral Breakdown Matrix

---

## 1. When all streams must complete

### `forkJoin`

- **Behavior:** **Yes, this is a strict requirement.** `forkJoin` will never emit anything until every single source stream completes. If even one stream remains open (like an active `BehaviorSubject`), the entire `forkJoin` hangs indefinitely.

### `combineLatest`

- **Behavior:** **No.** It does not wait for streams to complete to emit values. It emits actively as soon as all streams have provided at least one initial value. However, the combined stream itself will not emit its own `complete` notification until **all** underlying source streams have completed.

### `zip`

- **Behavior:** **No.** It emits continuously as pairs become available. However, it handles completion uniquely: the `zip` stream completes as soon as **any single** source stream completes _and_ no more matching index pairs can be created from the remaining buffered values.

### `withLatestFrom`

- **Behavior:** **No.** Its lifecycle is tied strictly to the primary source stream. The secondary streams do not need to complete. If the primary stream completes, the entire operator pipeline shuts down and completes, regardless of whether the secondary streams are still open.

---

## 2. When latest values are needed

### `combineLatest`

- **Behavior:** **This is its primary purpose.** Use this when you need a continuous stream that always reflects the most up-to-date combination of values. Whenever _any_ source stream emits a new value, it immediately pairs it with the latest cached values of all other peer streams.

### `withLatestFrom`

- **Behavior:** **Yes, but via a one-way master-servant relationship.** Use this when your primary trigger stream fires and needs to take a "snapshot" of the latest values from secondary streams. It peeks at the latest cached values of the secondary streams without being affected by their emission timing.

### `forkJoin`

- **Behavior:** **Only at the very final moment.** It ignores intermediate updates completely. It only captures the absolute last (latest) value emitted by each stream right before that stream closed.

### `zip`

- **Behavior:** **No.** It does not care about what value is chronologically "latest." It only cares about matching emission order ($N$-th value with $N$-th value).

---

## 3. When values should be paired

### `zip`

- **Behavior:** **This is its core definition.** Use this when values must be paired strictly by their **emission index/sequence order**. It pairs the 1st value of Stream A with the 1st value of Stream B, then the 2nd with the 2nd, completely ignoring chronological time gaps.

### `combineLatest`

- **Behavior:** **Paired by chronological timing.** It pairs values based on whatever is currently available in the stream cache at the moment of an emission. It creates a new pair every time any stream changes.

### `withLatestFrom`

- **Behavior:** **Paired on demand by the primary trigger.** It pairs the incoming value of the primary stream with the current background value of the secondary stream at that exact microsecond.

### `forkJoin`

- **Behavior:** **Paired exactly once at the end.** It aggregates the final values into a single, one-time combined bundle (array or object dictionary) right before shutting down.

---

## Quick-Reference Interview Cheatsheet

- If the interviewer says **"Parallel API calls where I need the final bundle"** $\rightarrow$ Think **`forkJoin`**
- If the interviewer says **"Live UI state changes / form filtering combo"** $\rightarrow$ Think **`combineLatest`**
- If the interviewer says **"Form submit click needs current auth token snapshot"** $\rightarrow$ Think **`withLatestFrom`**
- If the interviewer says **"Synchronized step-by-step batches / index matching"** $\rightarrow$ Think **`zip`**
