# Custom Observables

## What Is a Custom Observable

A custom Observable means you manually control:

- when values are emitted
- when stream completes or errors
- how resources are cleaned up

You create it with:

```ts
new Observable(subscriber => {
  // producer logic
});
```

---

## `new Observable()` Signature

Conceptually:

```ts
new Observable<T>((subscriber) => {
  // emit with subscriber.next(value)
  // finish with subscriber.complete()
  // fail with subscriber.error(err)

  // optional: return teardown logic
  return () => {
    // cleanup work
  };
});
```

`subscriber` gives you:

- `next(value)`
- `error(err)`
- `complete()`

Remember Observable contract:

- `complete()` and `error()` end the stream
- after end, no more `next()` values

---

## Basic Example

```ts
import { Observable } from 'rxjs';

const custom$ = new Observable<number>((subscriber) => {
  subscriber.next(1);
  subscriber.next(2);
  subscriber.next(3);
  subscriber.complete();
});

custom$.subscribe({
  next: (v) => console.log('value:', v),
  complete: () => console.log('done')
});
```

Output:

```text
value: 1
value: 2
value: 3
done
```

## Teardown Logic

Teardown logic is the cleanup code returned from the Observable callback.

It runs when:

- consumer calls `unsubscribe()`
- Observable completes
- Observable errors

Example with interval:

```ts
import { Observable } from 'rxjs';

const ticker$ = new Observable<number>((subscriber) => {
  let count = 0;
  const id = setInterval(() => {
    subscriber.next(count++);
  }, 1000);

  return () => {
    clearInterval(id);
    console.log('interval cleaned');
  };
});

const sub = ticker$.subscribe((v) => console.log(v));

setTimeout(() => {
  sub.unsubscribe();
}, 3500);
```

Without teardown, interval keeps running and can cause leaks.

---

## Cleanup Functions

A cleanup function should release anything started by producer logic:

- `clearInterval` / `clearTimeout`
- `removeEventListener`
- close socket / abort request
- stop observers or external subscriptions

DOM example:

```ts
import { Observable } from 'rxjs';

const clicks$ = new Observable<MouseEvent>((subscriber) => {
  const handler = (event: MouseEvent) => subscriber.next(event);

  document.addEventListener('click', handler);

  return () => {
    document.removeEventListener('click', handler);
    console.log('listener removed');
  };
});
```

---

## Common Mistakes

- forgetting to return teardown logic
- creating resources but not cleaning them
- calling `next()` after `complete()` or `error()`
- assuming Observable starts without `subscribe()`

---

## Interview Quick Lines

- `new Observable()` gives full producer control.
- Teardown logic is returned cleanup logic.
- Cleanup runs on `unsubscribe`, `complete`, and `error`.
- Missing cleanup is a common source of memory leaks.

## 5 Years Interview Depth (What Seniors Are Expected To Explain)

## 1. Execution Is Per Subscription

Custom Observable callback runs once per subscriber.

```ts
const obs$ = new Observable((subscriber) => {
  console.log('started');
  subscriber.next(Math.random());
});

obs$.subscribe(console.log); // started
obs$.subscribe(console.log); // started again
```

This proves default behavior is unicast unless shared.

## 2. Guard Against Emitting After Unsubscribe

In async producers, always stop work if subscriber is closed.

```ts
const obs$ = new Observable<number>((subscriber) => {
  const id = setInterval(() => {
    if (subscriber.closed) {
      clearInterval(id);
      return;
    }
    subscriber.next(Date.now());
  }, 1000);

  return () => clearInterval(id);
});
```

`subscriber.closed` helps avoid useless work and side effects.

## 3. Error Handling Inside Producer

If producer logic can throw, route it to `subscriber.error`.

```ts
const safe$ = new Observable<number>((subscriber) => {
  try {
    const parsed = JSON.parse('{"value": 10}');
    subscriber.next(parsed.value);
    subscriber.complete();
  } catch (e) {
    subscriber.error(e);
  }
});
```

Do not throw uncaught errors from async callbacks.

## 4. Teardown Must Be Idempotent

Teardown can be called more than once in complex chains.

- Write cleanup that is safe to execute repeatedly.
- Prefer APIs that naturally tolerate repeat calls (`clearInterval`, `removeEventListener` with same handler reference).

## 5. Sync vs Async Emission Matters

`next` can be synchronous in `new Observable`.

- synchronous emission can surprise UI code
- may trigger re-entrancy in consumers
- scheduler-based operators can control timing later

Interview note: mention when you would use `observeOn` or `subscribeOn` to control scheduling.

---

## Strong Scenario Answer (Memory Leak)

Question pattern:

"We used custom Observable for DOM events and saw memory growth. What happened?"

Strong answer:

1. Each subscription attached a listener.
2. Teardown did not remove listener or subscription never unsubscribed.
3. Detached components kept handlers alive.
4. Fix: return cleanup from `new Observable`, and ensure unsubscribe path (`takeUntil`, `AsyncPipe`, or explicit cleanup).

## Senior-Level Quick Q&A

Q: Why not always use `new Observable` directly?
A: Prefer built-in creators/operators for correctness and readability; use `new Observable` for integration boundaries (callbacks, sockets, browser APIs, custom resources).

Q: What is the difference between producer and consumer responsibility?
A: Producer emits and releases resources; consumer subscribes and decides lifecycle (`unsubscribe`).

Q: How do you test teardown?
A: Subscribe, trigger unsubscribe, assert side effects are cleaned (timer cleared, listener removed, socket closed).

Q: Can cleanup run on complete/error too?
A: Yes. Teardown is part of subscription disposal, not only manual unsubscribe.
