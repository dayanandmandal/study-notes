# Pipeable Operators

## What Are Pipeable Operators

Pipeable operators are functions used inside `source$.pipe(...)`.

Each operator takes an Observable and returns a new Observable.

So conceptually, every operator follows:

```ts
(input$: Observable<T>) => Observable<R>
```

This is why we say: Observable -> Observable.

---

## Why Pipeable Operators Exist

Before RxJS 5.5, operators were often patched onto `Observable.prototype` ("dot-chaining").

Pipeable operators improved this by:

- making imports explicit
- enabling better tree shaking
- avoiding prototype patch side effects
- making custom operator composition cleaner

---

## Observable -> Observable Mental Model

Given:

```ts
const result$ = source$.pipe(
  map(x => x * 2),
  filter(x => x > 10)
);
```

Flow:

1. `map(...)` creates operator function A.
2. A receives `source$`, returns `mapped$`.
3. `filter(...)` creates operator function B.
4. B receives `mapped$`, returns `filtered$`.

Nothing executes until `result$.subscribe(...)`.

---

## Operator Factories

An operator factory is a function that returns an operator function.

Example: `map(projectFn)`.

- `map(...)` is the factory
- it returns `(source$) => transformed$`

### Built-in Example

```ts
import { map, Observable } from 'rxjs';

const mapToLength = map((s: string) => s.length);
// mapToLength type: (source$: Observable<string>) => Observable<number>
```

You can reuse `mapToLength` in multiple pipelines.

---

## Building a Custom Operator Factory

Use `pipe(...)` (from RxJS) to compose reusable operator logic.

```ts
import { pipe } from 'rxjs';
import { filter, map } from 'rxjs';

export const normalizeAndValidateUser = () =>
  pipe(
    map((raw: { name?: string; age?: number }) => ({
      name: (raw.name ?? '').trim(),
      age: raw.age ?? 0
    })),
    filter((user) => user.name.length > 0 && user.age >= 18)
  );
```

Usage:

```ts
users$
  .pipe(normalizeAndValidateUser())
  .subscribe(console.log);
```

This is the same pattern as RxJS built-ins: factory -> operator function.

---

## `pipe` vs `pipe(...)` Utility

Two different things with same word:

- `observable.pipe(op1, op2)` runs operators on one stream
- `pipe(op1, op2)` creates a reusable operator chain (factory result)

Interview tip: explicitly clarify this difference.

---

## Type-Level View (Important for Senior Interviews)

You can describe operator types using `OperatorFunction<T, R>`.

```ts
import { OperatorFunction } from 'rxjs';

const toLength: OperatorFunction<string, number> = map((v) => v.length);
```

- input stream type is `T`
- output stream type is `R`

For no type change (e.g. `filter`), type is often `MonoTypeOperatorFunction<T>`.

---

## Common Mistakes

- thinking operators run immediately (they are lazy)
- creating side effects in `map` (use `tap` for side effects)
- writing custom operators that lose types (`any` everywhere)
- forgetting that each subscription re-runs chain unless shared (`share`, `shareReplay`)

## 5 Years Interview Depth

## 1. Explain With Internals Language

Strong line:

"A pipeable operator is a higher-order function. The factory captures config, then returns an operator function that accepts a source Observable and returns a new Observable with transformed subscribe behavior."

## 2. Why Factories Matter in Real Apps

Factories allow parameterized reusable logic:

- `debounceAndDistinct(300)`
- `handleHttpError('fetch users')`
- `requireRole('admin')`

This improves consistency across teams and reduces duplicated pipelines.

## 3. Performance/Behavior Angle

Operators do not copy values; they wrap subscription behavior.

That means understanding:

- where synchronous work happens (`map`, `scan`)
- where concurrency happens (`mergeMap`, `switchMap`)
- where multicasting changes execution count (`share`, `shareReplay`)

## 4. Testing Strategy

Custom operator factories should be unit-tested as pure stream transforms:

- input marble -> output marble
- edge cases (error, complete, empty)
- type expectations for compile-time safety

## Quick Interview Q&A

Q: Why are they called "pipeable"?
A: Because operators are passed into `.pipe(...)` and composed left-to-right.

Q: Is `map(fn)` itself the operator?
A: Strictly, `map(fn)` is an operator factory call result; the returned function is the operator function.

Q: What does Observable -> Observable mean?
A: Operator input is a source Observable; output is a new Observable representing transformed emissions.

Q: Can we create our own pipeable operators?
A: Yes, either by returning `(source$) => new Observable(...)` or more commonly by composing existing operators via `pipe(...)`.
